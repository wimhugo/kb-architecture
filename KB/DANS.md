# Product Requirements Document: DANS Documentation Corpus KB

## Intent & Goal

Consolidate a large, partially complete documentation corpus currently held in Google Drive (documents, presentations, PDFs, and IcePanel architecture diagrams) into a mature collection with one canonical document per distinct topic, published as Word, PowerPoint, Excel and PDF copies accessible independently of Google Drive. The corpus is managed as the 'DANS documentation' Knowledge Base within the established boRDMIk architecture: a Git repository holds the RDF schema, SKOS vocabularies, registries of instances, graph instances and release snapshots; this app is its curation workspace, following the KB Curation Platform's design principles: Git as source of truth with all writes via Pull Requests, configuration-driven pipelines, PROV-O provenance, and human-in-the-loop GenAI assistance. The app also serves as the public search and discovery client over the graph: it indexes the graph, resolves vocabulary and registry URIs to human-readable labels, and provides detailed resource views. A later phase extends the corpus with papers and resources from the web (often Zenodo) and less-organised project-grouped supplementary documents.

## Audience & Roles
Four role groups, aligned with the roles already defined in the existing automated curation applications, with functionality linked to roles. Public visitors (no login) browse, search, and download from the discovery interface. Contributors are authenticated users who register new resources and contribute annotations, metadata, and other information about resources. Curators are a small set of authenticated editors who manage the corpus (graph and optionally the resources themselves) and the vocabularies, with automated or assisted functions for importing the Drive inventory, classifying resources, marking placeholders and duplicates, designating canonical documents per topic, annotating with vocabulary keywords, and maintaining SKOS concept schemes and registries in the KB repository; they review Pull Requests in GitHub and amend automated decisions in the UI. Administrators are a few accounts authorised to configure the API based on the KB and client apps, and to edit settings such as the platform-default GitHub PAT, KnowledgeBase repository and credential definitions, provenance configurations, and new project and KB definitions. Curation screens are visible only to the appropriate roles; discovery is fully public.

## Core Flows
1. **Corpus import**: curator imports the Google Drive inventory (document list with metadata, e.g. a CSV export) through a configuration-driven pipeline following the Harvester/Data Sync pattern (tabular source transformed to RDF/TTL or JSON-LD); each document becomes a resource node in the KB graph, written as a branch + Pull Request
2. **Curation review**: an automated, GenAI-assisted routine inspects each resource and marks it as placeholder/duplicate/draft to discard, or promotes it as the canonical document for its topic; decisions are recorded in the graph, curators can manually revisit and amend the classification in a UI, and all changes reach the repository via Pull Requests
3. **Structure rule**: requirements and specifications live in a canonical topic library; project-specific modifications live in annexes; each project has a summary document that links the requirements and specifications applicable to it
4. **Diagram integration**: curator exports IcePanel architecture diagrams as PDFs and publishes them; an automated routine attempts to identify and link them with the resources they illustrate, with curators able to edit the links in a UI
5. **Presentation consolidation**: the same automated review-and-promote flow consolidates presentations into a smaller canonical subset, with curator review
6. **Publishing**: canonical documents are made available as Word, PowerPoint, Excel and PDF copies stored independently of Google Drive (app file storage or Drive), with stable URLs recorded as properties of the graph nodes
7. **Annotation**: curator annotates resources with keywords drawn from controlled vocabularies maintained as SKOS concept schemes and registries of instances (topics, projects) in the repository, reusing the Annotation Notes and Definition Synthesizer patterns (LLM synthesis with reviewable, editable output); edits to vocabularies and registries are written back to the repository via Pull Requests
8. **Metadata graph**: every resource is connected to topics, projects, keywords and other resources (relations such as supersedes, extends, annex-of, diagram-for), all persisted in the repository's graph instances
9. **Provenance**: every transformation records PROV-O provenance (what ran, when, on behalf of whom, on which inputs) into a configurable folder with overwrite/update/append modes, supporting retroactive back-fill from historical run metadata
10. **Public discovery**: visitor searches by free text or controlled keyword, browses by topic or project, and opens a resource detail page showing metadata, relationships and download/view links in all published formats, with URIs resolved to human-readable labels
11. **Release management**: snapshots of vocabularies, registries and graphs can be taken into a releases folder in the repository, associated with a specific release of the KB
12. **Administrator configuration**: administrators manage KnowledgeBase records (repository URL, branch, default folder, namespace, PAT), the platform-default GitHub PAT (resolution order: config PAT, then KB PAT, then platform default), provenance configurations, and new project and KB definitions
13. **Pipeline lifecycle**: each curation job is a configuration entity supporting create/edit/clone/delete with status draft/active/archived and last_run_at/last_run_summary; running a pipeline immediately surfaces the resulting Pull Request and per-row errors
14. **Navigation**: workspace-based navigation with a dashboard of stat cards and recent-run feeds, and a shared KB/Project filter bar narrowing every curation list page and the dashboard to one Knowledge Base and/or Project
15. **Later phase**: curator ingests web/Zenodo papers and less-organised project-grouped supplementary documents through the same annotation and classification flow, and the graph structure allows later combination with other boRDMIk knowledge bases since resources may be shared while each KB classifies them differently

## Technical Requirements
Follow the established Knowledge Base architecture and the KB Curation Platform design principles. A Git repository (kb-dans-documentation, GitHub) is the canonical store for the RDF schema (classes and properties), SKOS vocabularies, registries of important instances (topics, projects), graph instances, a releases folder with snapshots, and support documentation. Git is the source of truth: all generated artefacts (TTL, JSON-LD, SHACL, inventory files) are written as a GitHub branch + Pull Request, never a direct commit and never an opaque store; each run returns file count, PR number/URL and per-row errors, and updates the configuration's last_run_at/last_run_summary. Curation is configuration-driven: each pipeline has its own config entity; configurations inherit repository URL, branch, folder and credentials from their linked KnowledgeBase when blank, with GitHub PAT resolution centralised in a shared helper (config PAT, then KB PAT, then platform default in PlatformSetting); a workspace-registered GitHub OAuth connector ('OpenREL Github') plus fine-grained PATs mediate GitHub access. GenAI assistance uses the platform's InvokeLLM integration for first-pass classification, diagram-to-resource linking, keyword suggestion and definition synthesis, always human-in-the-loop: output is reviewable/editable and final writes go through PRs. PROV-O provenance is first-class for every transformation, with overwrite/update/append modes and retroactive back-fill. Binary outputs (Office/PDF) are NOT stored in the repository: they live in app file storage or Drive with stable URLs referenced as properties of the graph nodes. Use Base44 built-ins directly (entities, SDK, InvokeLLM, UploadFile, GitHub connector), with custom backend functions only for GitHub orchestration and domain logic, and shared logic in shared modules. Role-gated access: public discovery requires no authentication; contributor, curator and administrator functions each require authentication and the matching role, enforced per function. The UI follows the platform's patterns: workspace switcher navigation, config list pages (cards with edit/clone/delete) plus run pages, tabbed config forms, a shared ConfigFilterBar for KB/Project filtering, React Query for state, and responsive layout for mobile, tablet and desktop.
